# Auth0 + Google setup

The application now uses Auth0 for authentication and Google as the social identity provider. Supabase/PostgreSQL and the existing Prisma schema are unchanged.

## Auth0 dashboard

1. Keep the SPA application already created for this project.
2. Enable **Google** under Authentication -> Social.
3. Under the SPA application settings, add your local frontend URL to:
   - Allowed Callback URLs
   - Allowed Logout URLs
   - Allowed Web Origins
4. Create an Auth0 **API** for the library backend.
   - Identifier: choose a stable value such as `https://library-management-api`
   - Signing Algorithm: RS256
5. Use that API Identifier as both:
   - `VITE_AUTH0_AUDIENCE`
   - `AUTH0_AUDIENCE`

The API middleware validates the Auth0 access-token signature against the tenant JWKS, issuer and audience before loading the Auth0 user profile.

## Local environment

Copy the example files:

```bash
cp client/.env.example client/.env
cp server/.env.example server/.env
```

Set:

```text
VITE_AUTH0_DOMAIN=dev-drh4iui2l24tmtsm.us.auth0.com
VITE_AUTH0_CLIENT_ID=<your client id>
VITE_AUTH0_AUDIENCE=<your Auth0 API Identifier>
VITE_AUTH0_GOOGLE_CONNECTION=google-oauth2
```

On the server:

```text
AUTH0_DOMAIN=dev-drh4iui2l24tmtsm.us.auth0.com
AUTH0_AUDIENCE=<your Auth0 API Identifier>
DATABASE_URL=<existing Supabase Postgres connection string>
```

Do not commit `.env` files or secrets.

## Install the frontend dependency

From `client/`:

```bash
npm install
npm run build
```

The repository's existing package lock should be regenerated by npm after adding the Auth0 dependency.

## Database

No Prisma model, migration, or database table was changed.

When a new Google user signs in, the backend creates the existing `User` record using the current schema and assigns the existing default `STUDENT` role. Existing users are matched by email and keep their existing role and relationships.
